## 尼泊尔右手「在后背动」终极根因：镜像公式错误（2026-08-23 上午）
- 用户反馈：右手肩部旋转 180° 在后背动。**根因 = 左右镜像公式错了**。
- **关键数学（probe_mirror_math 实证）**：左右镜像本质是**反射（det=-1）**，无法用「绕单轴 180° 旋转共轭」实现！
  - 旧公式 qY180·q·qY180（绕 up 共轭）= (w,-x,y,-z)：前伸→**后伸**（前后翻转）→ 右手在后背 ✗
  - **正确公式：q' = (x, -y, -z, w)（四元数 y、z 分量取反）**= 镜面「X（左右轴）取反」的反射共轭：前伸→前伸 ✓、左平举→右平举 ✓、上下不变 ✓
  - 反射共轭数学：M·Q·M⁻¹ = 绕轴 M·a 转 **-θ**（角度也反号）→ 四元数 (w, -M·a·s) 展开得 (w,x,-y,-z)
- **⚠️ Godot Quaternion 构造顺序 = (x, y, z, w)**！写 `Quaternion(w,x,y,z)` 会静默错乱（镜像实验首次假失败就是这个）。轴角构造 Quaternion(axis, angle) 不受影响。
- 修复：build_nepal_right_hand.gd 的 `_mirror` → `Quaternion(q.x, -q.y, -q.z, q.w)`；probe_verify_right_hand 目标同步改。重新烘焙（idle 121帧 2.0s 等）。
- 验证：数学 0.03° ✓；probe_direction 方向检查：FP 左手骨骼方向 左+上 → 镜像后 右+上（左右翻、前后保持 ✓）。
- ⚠️ 镜像公式与角色前向（±Z）无关：只要「右=+X、上=+Y」，反射就是 X 轴取反 → q'=(x,-y,-z,w) 恒成立（本项目角色朝 +Z 也适用）。
- 遗留：用户在自己 GUI Blender 导入 nepal_kukri_viewmodel.gltf 显示「一个球」，待用户提供导入方式/截图排查（headless 导入验证过网格正常：hand__hands + weapon__ref-1/2/3）。

## 尼泊尔刀→枪崩溃修复（2026-08-23 晚）
- 用户报告「切到刀，再切枪，游戏直接崩溃」。经二分定位 + 数据级验证，**根因不是尼泊尔合成动画本身，而是三个叠加问题**：
- **① 坏轨道路径（日志洪水放大器）**：`resources/characters/anim_clips_feihu.tres`（及 swat/registry 内嵌各 89 条）的轨道是旧式 `NodePath("Armature/mixamorig_Hips")`，Godot 4 需 `Armature/Skeleton3D:mixamorig_Hips`。整库轨道永远解析不了，`install/remove_animation/stop` 每次重建缓存都刷 45+ 条警告 + backtrace（伪装成 `_update_caches` 崩溃噪音）。修复：`tools/fix_clip_track_paths.py` 全项目批量改 `Armature/mixamorig` → `Armature/Skeleton3D:mixamorig`（929 处）。该 `clips` 库与主库 `mixamo_lib.tres` 的 `Toss Grenade` 同名冗余，纯噪音源。

- **③ 姿态顺序 Bug**：原代码先 `_apply_pistol_stance(def.id=="v_deagle")` 再 `_apply_nepal_stance(def.id=="nepal_kukri")` —— 切到尼泊尔时 pistol 合成已写进库、随后 nepal 覆盖；但切走时反过来：nepal 先清、pistol 后清，两者备份互相覆盖导致残留。修复：改为「先判断是否尼泊尔，是则只跑 nepal、跳过 pistol；否则两个都跑（pistol 最后写，最终态正确）」即 `_want_nepal` 短路。

- **关键诊断经验**：headless（RendererDummy）下 `_update_caches` 只打印 backtrace、不打印 SCRIPT ERROR，且**致命崩溃在 headless 下不致命**（EXIT=0），必须用 `_process` 驱动探针（非 await 协程，协程会吞 message）；更关键是**不要数 backtrace**，要 grep 真正的 `^ERROR:` 与 `SCRIPT ERROR:`（那些 `_update_caches` 全是 `character_preview.tscn` 的 Toss Grenade 噪音）。
- 保留回归探针：`tools/probe_fatal.gd`（切刀时序 4 场景）、`tools/probe_stance_data.gd`（姿态数据级还原验证）、`tools/probe_switch_real.gd`（真实切枪路径）。

## FP 视图模型重复 LOD 清理（2026-08-23 晚3）
- 用户反馈：Blender 打开导出的 nepal_*.gltf 后，模型被「层层球体白模包裹着，放大到最里边才能看到」。
- **根因**：源 gltf 的 4 mesh 中，`weapon__ref-1` 与 `weapon__ref-2` **顶点级完全相同**（822 顶点，bbox 完全一致）——Source 引擎近景/远景 LOD 的两份重复几何，被 SourceIO 一起输出。所有 ref 都挂在 Skeleton3D 下被 skin 蒙皮（不是无蒙皮占位）。
- **修复**：`tools/clean_nepal_fp_gltf.py` 删 `weapon__ref-2`（ref-1 的精确副本），保留 hand + ref-1（刀身）+ ref-3（刀刃薄面）。同步从 .godot 缓存 `.scn` 恢复源 .gltf（中途误删了 ref-* 所有 mesh 节点，用 GLTFDocument 加载 `.scn` 缓存 → append_from_scene → write_to_filesystem 重新生成 user:// 临时 .gltf，再回写源）。
- **教训**：FP 视图模型从 CS 武器导出时，SourceIO 经常输出重复的 LOD 副本，不要把 `weapon__ref-*` 误当"参考几何"全删——它们是刀本体。
- **输出**：`fp_viewmodel/nepal/exports/{nepal_idle,nepal_light,nepal_heavy}.gltf` 现各含 3 mesh（hand+ref-1+ref-3），无层叠。
- **二次事故（Bin 截断）**：用户报 "Couldn't parse glTF"。查因：`exports/nepal_kukri_viewmodel.bin` 仅 1070632 字节，但 gltf 声明 `byteLength=1584224` → Blender 读到一半数据不够直接报错。源 bin 完整 1584224 字节。根因：`split_nepal_fp_gltf.py` 复制 bin 时落到了误删 ref 那版的残片（1.07MB）。**修复**：`cp` 完整源 bin 覆盖 exports/bin，三个文件 decl==real 校验通过，严格引用校验 0 问题。
- **铁律**：拆分/复制 glTF 后**必须**校验 `gltf 声明的 buffer.byteLength == 实际 .bin 文件字节数`，否则 Blender 报 "Couldn't parse glTF"。bin 是共享大文件，复制务必指向完整源。
- **三次事故（GODOT_single_root 扩展）**：bin 修好后仍报 "Couldn't parse glTF"。**真根因**：Godot 导出的 glTF/glb 在 `extensionsUsed: ["GODOT_single_root"]` 写了扩展名，但 `extensions` 对象为空（Godot 4.7 的已知导出 bug）——声明了扩展却无数据，Blender 严格解析器找不到对应数据直接失败。JSON 语法、bin 大小、引用范围全对也会栽在这。**修复**：①用 Godot `GLTFDocument.append_from_scene` 从 `.godot/imported/*.scn` 缓存重新干净导出 `.glb`（单文件最稳）；②`tools/strip_godot_ext.py` 剥离 `extensionsUsed` 里的 `GODOT_single_root`（对 Blender 无意义）。`.gltf` 分离版同样需要剥离。
- **最终交付**：`fp_viewmodel/nepal/exports_glb/{nepal_idle,nepal_light,nepal_heavy}.glb`（推荐用这个，单文件无扩展残留，Blender 直接拖入即可）+ `exports/` 下 `.gltf` 版（需配同目录 .bin+textures）。所有文件 ext=None、decl==real、anim 单体。
- **四次事故（几何层叠"包裹球"）**：Blender 打开后仍有"球包裹手"。查因：源 4 mesh = hand + **weapon__ref-1（刀身）+ weapon__ref-2（ref-1 的精确副本，822 顶点/bbox 完全一致，两把刀重叠）+ weapon__ref-3（140×46 的 Z≈0 大薄片，Source 物理/刀光代理面）**。ref-2 重叠 + ref-3 大面 = 视觉包裹。**修复**：`tools/remove_ref2_from_glb.py` 从 glb 里删 `weapon__ref-2` 和 `weapon__ref-3` 的 node+mesh（不碰 accessor/bin，仅重映射 node/mesh 索引），最终每个 glb 只留 `hand__hands` + `weapon__ref-1`（手+真实刀身）。注意：手 bbox ±95（米级，Source 单位，正常），无 node transform（靠 skin 蒙皮驱动）；骨骼名是 GBK 乱码（"用户名1"等），Blender 里若绑定异常需另查。
- **导出流程铁律（回顾）**：①Godot `GLTFDocument.append_from_scene` 从 `.scn` 缓存导出 → ②`strip_godot_ext.py` 剥 `GODOT_single_root` → ③`remove_ref2_from_glb.py` 剥 ref-2/ref-3 重叠/代理几何。三步顺序不能省。另：清 `.godot/imported` 缓存会让 `.scn` 源丢失，`_export_nepal_glb.gd` 需改读 `.gltf` 源（但 headless load .gltf 不触发导入，故最终用 Python 直接改 glb 更稳）。
