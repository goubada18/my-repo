一、执行摘要Executive Summary

项目整体功能骨架完整、核心玩法闭环已经跑通：启动预加载 → 主菜单/地图/角色选择 → 5 武器（AK47 / 沙漠之鹰 / 尼泊尔军刀 / 高爆 / M82A1）× 2 角色（飞虎队 / SWAT）× 第一/第三人称切换，且换弹的 1P/3P 相位同步、AnimationCombiner 的防崩溃安装等细节做得相当扎实。日志显示三周内经历了 14 个高强度开发日、上百轮修复迭代，工程韧性惊人。

但审查发现三类必须尽快处理的风险：

① 发布即坏的隐形炸弹。M82 全部音效走 .wav 原始字节解析（audio_wav_loader.gd），而 .wav 已被 Godot 导入器接管——编辑器里一切正常，导出 PCK 后 M82 会整体静音。类似"编辑器内测不出来"的问题还有 boot 预加载对失效路径会永久卡死。

② 状态机边角泄漏。蹲下打断换弹、换弹中按 R 等路径不走统一收尾函数，会泄漏 _is_reloading 标志、让换弹音效失控播放，直到玩家再次开火/切枪才自愈。

③ 工程卫生债务集中爆发。player.gd 单文件 4865 行（占全部代码 41%）；15.7MB 的 demo_broken_backup_20260827 旧版快照混在工程内；4 个场景内嵌 Base64 图像、两个 3.7MB 动画库文本；.gitignore 缺口叠加历史上两次 git 事故（08-24 仓库损坏、08-28 index 丢失），版本管理是这个项目当前最脆弱的一环。

三、系统架构解读Architecture

3.1 运行链路

boot.tscn（线程化预加载进度条）→ main_menu.tscn（角色/地图选择，写入 GameState）→ main_multichar.tscn（CharacterManager 挂角色 → player.gd 接管）。预加载队列来自 character_registry.tres，因此该 542KB 资源成为全部重型依赖（两个 3.7MB 动画库 + 2MB character.tscn 等 12+ 资源）的汇聚点，主菜单前需加载约 10MB。

3.3 武器系统数据流

WeaponDef.tres（数值/音效/FP 场景/动画映射）→ WeaponSystem（只管"当前武器数据"）→ player.gd 在切枪时把 fire_rate、音效路径、FP 配置逐字段注入三套子系统。3P 层：WeaponRig 每帧把世界枪对齐到双手连线（握持偏移按 0.00026/骨架缩放 跨骨架换算）；FPActionRetarget 用程序化包络模拟 3P 射击/刺刀。FP 层：FPViewmodelPlayer 把 viewmodel 挂在主相机下，运行时烘焙"dup + *_preview 重命名 + 回位尾巴/呼吸叠加"。武器差异（连发/单发、能否开镜、3P 摆位）目前以 id 字符串硬编码在 player.gd，未完全数据驱动。

3.4 动画管线

3P 常规状态由动画状态机直驱；换弹/挥刀/投掷走"一次性覆盖"；换弹 = AnimationCombiner 静态合成（上半身换弹 × 下半身移动铺满），1P/3P 用 _reload_elapsed 统一时钟对齐（此机制是全项目做得最细的部分，含掉线自愈 player.gd:2613）。上半身俯仰由 Spine 轨道叠加实现。跨角色换皮采用"动画库坐标换算"生成 mixamo_lib_swat.tres，不改网格。

值得肯定的正面项：换弹 1P/3P 相位同步与掉线自愈；AnimationCombiner 安装时"先 stop 再 remove"防 dangling track 崩溃；boot→GameState 缓存 registry 规避 Godot 4.7 二次 load 崩溃；debug 门控开关（DEBUG_MODE/NEPAL_LOG）机制设计（虽未贯彻到底）。

四、A · 功能性缺陷Runtime Bugs · 15 项

这些问题会或早或晚在实际游玩中触发。✓ 已复核 表示本次审查由人工直接读码/命令验证过；日志已知 表示 .workbuddy 日志中已有记录。

A1 高危 boot 预加载遇到失效路径会永久卡死在进度条 ✓ 已复核
位置：scripts/boot.gd:105-128
func _start_next() -> void:
    var p: String = _queue[_idx]
    if ResourceLoader.exists(p):
        ResourceLoader.load_threaded_request(p, "", true)   # 不存在时不发起请求也不推进 _idx
# _process 只处理 LOADED / FAILED / IN_PROGRESS 三种状态

后果：若任何一个武器 .tres 里的 fp_viewmodel_scene/配置路径写错或文件被移动，load_threaded_get_status 返回 THREAD_LOAD_INVALID_RESOURCE，三个分支都不命中 → 进度条永远停在"加载资源 X / Y"，游戏无法进入主菜单且没有任何报错。这是"改了资源路径 → 游戏卡加载"这类玄学问题的标准成因。

建议：对 THREAD_LOAD_INVALID_RESOURCE 增加兜底分支（跳过并 push_warning 打印路径）；exists(p) 为假时也推进 _idx。

10.3 关键技术决策（供后续维护者了解"为什么是现在这样"）
